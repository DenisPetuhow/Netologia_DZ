Что касается рекомендаций. Возьмем поиск по ключевым словам. Запрос корректный. Обратите внимание, что использование LOWER() делает поиск нечувствительным к регистру, но может препятствовать использованию индекса по столбцу name. Если производительность станет проблемой в реальном проекте, рассмотрите возможность использования индекса на выражение (CREATE INDEX ... ON trek (LOWER(name))) или полнотекстового поиска. поясни

Когда вы пишете:
sql
копировать
WHERE LOWER(name) LIKE '%my%'
PostgreSQL вынуждена применять функцию LOWER() к каждому значению столбца name, а уже потом сравнивать с шаблоном.
Из-за этого:
Обычный B-tree-индекс по name использоваться не будет – в нём хранятся исходные значения, а не приведённые к нижнему регистру.
Сканируется вся таблица (SeqScan) – на больших объёмах становится медленно.
Что делать, если поиск станет узким местом?
Индекс на выражение (functional index)
Создаём индекс именно по нижнему регистру:
sql
копировать
CREATE INDEX trek_name_lower_idx ON trek (LOWER(name));
Теперь WHERE LOWER(name) LIKE '%my%' способен использовать Bitmap Index Scan по этому индексу (если остальные условия позволяют).
Полнотекстовый поиск (GIN + to_tsvector)
Для естественного языка лучше использовать FTS:
sql
копировать
ALTER TABLE trek ADD COLUMN name_fts tsvector
GENERATED ALWAYS AS (to_tsvector('simple', name)) STORED;

CREATE INDEX trek_name_fts_gin ON trek USING GIN (name_fts);

-- запрос
SELECT *
FROM   trek
WHERE  name_fts @@ plainto_tsquery('simple', 'my');
ищет слова, а не подстроку;
работает через GIN-индекс – быстро даже на миллионах строк;
нечувствителен к регистру и окончаниям автоматически.
Итого: LOWER() удобен для простых задач, но при росте данных нужно либо создавать functional-индекс, либо переходить на полнотекстовый поиск.
